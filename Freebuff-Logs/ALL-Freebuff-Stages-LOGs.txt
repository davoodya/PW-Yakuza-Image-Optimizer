## Recommendation: Stage 1 = The Core Processing Pipeline

Start by making `yio_process_uploaded_image()` **actually do the full job**: backup → load → resize/orient → convert to WebP/AVIF → save → update the database. This is the architectural keystone of the entire plugin, and here's why it has to come first:

**1. Everything else plugs into it.** The watermark and SEO engines are pure functions that take an Imagick object and return it — they're meaningless until the pipeline actually loads an image, calls them, and saves the result. Building them first means testing them in isolation against code that doesn't exist. Building the pipeline first gives every later engine a real home.

**2. It's the highest-risk part — de-risk it early.** The hard 20% of this plugin isn't compression; it's keeping WordPress's database and metadata consistent when you swap `photo.jpg` for `photo.webp`. This means updating `_wp_attached_file`, the post `guid`, the mime type, deleting stale JPG size variants, and regenerating thumbnails *without* re-triggering our own filter (infinite loop risk). If we get this architecture wrong, watermark and SEO work is wasted. Getting it right first makes the rest trivial.

**3. It delivers real value fastest.** After Stage 1, users can upload an image and get a compressed WebP/AVIF with a backup of the original — the #1 advertised feature — even before watermark/SEO exist.

**4. Bulk & Restore depend on the same core routine.** `bulk.php` (missing) just loops attachments through the *same* single-image process function. `restore.php` (missing) is the reverse. Both are thin wrappers — but only once the core routine is real.

---

## Scope of Stage 1 (concrete)

- Fix the hardening issues that would break testing anyway: strip UTF-8 BOMs from all 13 files, remove the dead `yio_logger_init()`/`yio_bulk_init()` calls, delete the duplicate `background_processing` key, fix the `max_width` default mismatch, and give `watermark_image` proper `absint` sanitization.
- Rewrite `yio_process_uploaded_image()`:
  - Backup original via the existing `yio_create_backup()` (respecting `backup_original` setting)
  - Smart resize (if `max_width` exceeded) + auto-orientation
  - Invoke `yio_apply_watermark()` and `yio_apply_seo_optimization()` (no-ops for now, so they're *wired* and tested)
  - Convert to WebP/AVIF with `image_quality`, honoring the AVIF-fallback logic already in `yio_output_extension()`
  - Replace the upload file, delete old JPG/PNG + its stale size variants, update `_wp_attached_file`, `guid`, mime, and regenerate sizes via `WP_Image_Editor` directly (never through the filtered hook)
- Wire `yio_apply_watermark`/`yio_apply_seo_optimization` signatures now so Stages 2–3 drop in without touching the pipeline again.

## The full roadmap after Stage 1

| Stage | Deliverable |
|---|---|
| **1** | Core pipeline (above) — images compress & convert end-to-end |
| **2** | Watermark engine — PNG composite + text annotation (scale/opacity/position/padding) |

## Two design decisions to lock before I write code

1. **Replace-in-place**: the optimized WebP keeps the original filename base and replaces the uploaded file (original preserved in `original-img/`). This keeps URLs and `restore_method` semantics working — I assume this matches your intent given the existing backup structure.
2. **Regeneration strategy**: I'll regenerate size variants through the low-level image editor to avoid recursive filter calls, rather than the prefilter approach that rewrites file types before WordPress sees them.
